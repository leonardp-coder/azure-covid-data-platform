# Azure SQL Database — Staging and Analytical Warehouse

## 1. Overview

Azure SQL Database serves as the relational analytical warehouse for the Azure COVID Data Engineering Platform.

The Gold datasets generated by Azure Databricks are exported as Parquet files to ADLS Gen2 and loaded into Azure SQL staging tables.

SQL stored procedures validate and transfer the staging data into the analytical schema.

The warehouse provides structured dimensional data for downstream Power BI reporting.

## 2. Database Schema Organisation

The database uses three logical schemas:

| Schema | Purpose |
|---|---|
| `staging` | Holds incoming datasets before analytical loading |
| `analytics` | Contains the final dimension and fact tables |
| `audit` | Stores pipeline execution, load-control and rejected-record information |

This separation provides a clear boundary between incoming data, analytical data and operational audit information.

## 3. Staging Layer

The staging schema contains seven tables corresponding to the Gold datasets.

### Dimension staging tables
- `staging.dim_country`
- `staging.dim_date`
- `staging.dim_age_group`

### Fact staging tables
- `staging.fact_covid_daily`
- `staging.fact_hospital_daily`
- `staging.fact_hospital_weekly`
- `staging.fact_population_age`

The staging layer receives data exported from the Gold Delta tables.

It acts as an intermediate loading area before data is transferred into the analytical warehouse.

## 4. Analytics Layer

The analytics schema contains the final dimensional model.

### Dimension tables
- `analytics.dim_country`
- `analytics.dim_date`
- `analytics.dim_age_group`

### Fact tables
- `analytics.fact_covid_daily`
- `analytics.fact_hospital_daily`
- `analytics.fact_hospital_weekly`
- `analytics.fact_population_age`

The analytical tables maintain the relationships and constraints required for reporting.

The daily COVID fact permits null country keys for regional aggregate records that do not map to a country-level dimension record.

## 5. Stored Procedure-Based Loading

The SQL loading process uses stored procedures to manage the transfer of data from staging into the analytics schema.

The full-load procedure is responsible for:

1. Validating the incoming staging data.
2. Checking duplicate records.
3. Validating foreign-key relationships.
4. Loading dimension tables.
5. Loading fact tables.
6. Recording execution and load information.
7. Handling failures and returning errors to the calling process.

Dimensions are loaded before fact tables to maintain referential integrity.

## 6. Full-Refresh Loading Strategy

The current warehouse implementation uses a full-refresh loading strategy.

Existing analytical data is removed and reloaded from staging as part of the full-load process.

This approach is suitable for the static datasets used in this project.

The implementation does not use incremental loading or Change Data Capture.

## 7. Transaction Management and Error Handling

The full-load procedure uses SQL transaction management to control the loading operation.

Key implementation practices include:

- `SET XACT_ABORT ON` to help manage transaction failures.
- `TRY...CATCH` for exception handling.
- Explicit transaction handling.
- `THROW` to propagate errors to the calling process.

These mechanisms help prevent failed loading operations from being silently treated as successful.

## 8. Audit and Failure Logging

The audit schema contains operational tables used to track pipeline execution, loading activity and rejected records.

The project also includes a failure-logging stored procedure to capture execution failures.

This provides operational visibility into the SQL loading process and helps with troubleshooting.

## 9. Security and Permissions

The project includes SQL security scripts for the Azure Data Factory service principal.

The service principal requires the appropriate permissions to:
- Access staging and analytics objects.
- Insert and validate staging data.
- Execute the relevant stored procedures.
- Write audit and failure information where required.

Permissions should follow the principle of least privilege.

Secrets and credentials should not be committed to the public GitHub repository.

## 10. Data Validation

The warehouse loading process includes validation for:

- Duplicate business keys.
- Foreign-key integrity.
- Required data and schema compatibility.
- Source and target record counts.
- Rejected records and execution failures.

The validation scripts are maintained separately under the SQL validation folder.

## 11. SQL Source Organisation

The SQL scripts are maintained under the repository's `sql/` directory.

The scripts are separated by responsibility:

- Database schema setup.
- Staging table creation.
- Analytics table creation.
- Audit objects.
- Stored procedures.
- Security permissions.
- Validation queries.

This organisation supports easier deployment, maintenance and version control.

## 12. Design Considerations

- Separate staging from analytical tables.
- Use stored procedures to centralise loading logic.
- Load dimensions before facts.
- Use transactions and exception handling.
- Maintain audit information for operational visibility.
- Validate data before analytical loading.
- Use controlled service-principal permissions.
- Maintain SQL scripts under source control.
